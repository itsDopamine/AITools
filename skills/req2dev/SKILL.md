# req2dev — 需求转开发方案

将产品需求文档（PRD）+ UI 设计 + API 文档，转化为可落地的开发方案。

## 文档命名与落盘规范（强制）

**文档根目录**（下文记为 `{DOC_ROOT}`）：优先使用工作区下的 `./idoc`；若不存在则创建之。勿在 skill 或示例中写死本机绝对路径。

- 正式文档：`{DOC_ROOT}/`
- 临时材料：`{DOC_ROOT}/tmp/`

### 正式文档（`{DOC_ROOT}/`）

```
【{类型}】{需求短名}[-{范围}].md
```

| 类型 | 用途 | 对应阶段 |
|------|------|----------|
| `开发方案` | 与技术栈无关的通用方案 | Phase 1 |
| `实施方案` | 落在具体仓库/端的实施细节 | Phase 2 |
| `技术方案` | 非 req2dev 两阶段流程的其它技术设计 | 其它 |

**命名规则：**

1. 使用中文书名号式前缀 `【类型】`，类型仅上表三者之一（勿混用「通用开发方案」「Phase1」等别名）。
2. `{需求短名}`：去掉 PRD 前缀噪音（如 `【AI】`、日期），保留可读业务名；可用中文；单词间用空格或直接连写，**文件名内不用空格**，必要时用 `-`。
3. `{范围}`（可选）：项目仓或端，如 `meeting_web`、`PC前端`、`meeting_work`。Phase 2 涉及多仓/多端时建议带上。
4. **禁止** `req2dev-` 前缀、`Phase1`/`Phase2` 英文阶段号、全大写英文通用名（如 `IMPLEMENTATION_PLAN.md`）作为正式方案文件名。
5. 文件名与文档一级标题保持语义一致（标题仍可用 `【开发方案】{需求名称}` / `【实施方案】{需求名称} — {项目/端}`）。

**示例：**

| 正确 | 错误 |
|------|------|
| `【开发方案】离线声纹识别.md` | `req2dev-离线声纹识别-Phase1-通用开发方案.md` |
| `【实施方案】离线声纹识别-PC前端.md` | `【实施方案】离线声纹识别.md`（多端时缺范围，易混淆） |
| `【实施方案】转写错词自动替换-meeting_web.md` | `转写错词-meeting_web实施方案.md` |
| `【技术方案】企业会议存储管理-录制清理.md` | `企业会议存储管理-录制清理-技术方案.md` |

### 临时文件（`{DOC_ROOT}/tmp/`）

```
req2dev-{slug}-prd.md
req2dev-{slug}-api.md
req2dev-{slug}-prd-images/
```

- `{slug}`：需求短名的简写（中文或拼音/英文均可，保持同一次任务内一致）。
- 仅作导出与分析中间态，**不作为正式交付物**；正式方案写完后可保留或清理，勿与 `{DOC_ROOT}` 根目录正式文档混放。

## 核心理念

需求到代码之间有一个容易被忽视的「方案设计」环节。直接从需求跳到编码，会导致：
- 遗漏跨端/跨仓库的影响面
- UI 细节与设计稿偏差
- 接口字段理解偏差
- 业务规则覆盖不全

本 skill 把这个环节结构化为两个阶段：
1. **Phase 1（通用开发方案）**：与项目技术栈无关，关注「做什么」
2. **Phase 2（项目实施方案）**：落在当前代码仓库，关注「怎么做」

Phase 1 是必须执行的，Phase 2 在 Phase 1 完成并确认后，由用户决定是否继续。

## Phase 0：环境校验

在执行任何分析之前，必须先检查工具链是否就绪。根据用户提供的资源类型，逐项校验：

**始终校验（需求文档链接是必须的，而读取金山文档依赖 wps-doc-cli）：**

```bash
wps-doc auth --status
```

- 如果命令不存在（`command not found`）→ 提示用户：`wps-doc-cli 未安装，请先执行 npm install -g @wps-agent/core@latest --registry=https://registry.npmjs.org/ 安装`
- 如果返回未认证 → 提示用户：`请先执行 wps-doc auth 完成认证`
- 通过 → 继续

**如果用户提供了 Figma 链接，额外校验：**

检查当前环境是否有 Figma MCP 工具可用（查看 `mcps/plugin-figma-figma/` 目录是否存在且包含工具描述文件）。

- 不可用 → 提示用户：`Figma MCP 插件未配置，无法读取 Figma 设计稿。请在 Cursor 中启用 Figma MCP 插件，或者将设计稿导出为图片后提供给我`
- 可用 → 继续

**校验不通过时不能继续后续流程。** 逐项列出未通过的校验项和解决方法，等用户处理完毕后再继续。

## Phase 1：通用开发方案

### 1.1 收集输入

用户会提供以下资源（逐项确认）：

| 资源 | 必须 | 获取方式 |
|------|------|----------|
| 需求文档链接 | 是 | 使用 `/wps-doc-cli` 的 `wps-doc export` 读取 |
| UI 设计（Figma 链接 / 图片） | 否 | Figma 链接用 MCP Figma 工具读取；图片用 Read 工具查看 |
| API 文档链接 | 否 | 使用 `/wps-doc-cli` 的 `wps-doc export` 读取 |
| 其他补充材料 | 否 | 视情况处理 |

**如果用户未提供需求文档链接，必须主动索要。** 没有需求文档就没有分析的基础。

UI 和 API 文档不是必须的——有些需求在早期阶段可能只有 PRD，设计稿和接口文档还没出。但如果用户提供了，就必须读取并纳入分析。

### 1.2 理解需求

依次完成以下步骤（每一步的输出都是下一步的输入）：

**Step 1：读取需求文档**

```bash
wps-doc export "<需求文档URL>" -o "{DOC_ROOT}/tmp/req2dev-{slug}-prd.md"
```

通读文档，提取：
- 功能目标（这个需求要解决什么问题）
- 涉及的用户角色和场景
- 涉及的平台/端（PC、iOS、Android、H5、小程序…）
- 核心业务规则
- 边界条件和异常场景

**Step 2：读取 UI 设计（如有）**

- Figma 链接：使用 Figma MCP 工具的 `get_design_context` 获取设计上下文和截图
- 图片文件：使用 Read 工具查看

从 UI 中提取：
- 页面/组件清单（每个独立的 UI 模块）
- 交互行为（触发方式、动画、状态切换）
- 视觉规格（关键尺寸、色值、字号——不需要穷举，关注与业务相关的差异化样式）
- 条件展示逻辑（什么情况显示/隐藏某个元素）

**Step 3：读取 API 文档（如有）**

```bash
wps-doc export "<API文档URL>" -o "{DOC_ROOT}/tmp/req2dev-{slug}-api.md"
```

提取：
- 接口列表（URL、Method、鉴权方式）
- 请求/响应字段结构
- 字段含义和取值范围
- 错误码
- 特殊约定（如：某些字段由服务端控制，前端直接渲染不做判断）

### 1.3 影响面评估

这是容易遗漏的关键步骤。

根据需求理解，判断：
1. 这个需求涉及哪些平台/端？
2. 每个端需要改动哪些模块/页面？
3. 是否涉及多个项目仓库？

**必须询问用户：**

> 根据需求分析，本次需求涉及以下平台/模块：
> - [列出所有涉及的平台和模块]
>
> 当前项目仓库是 `{仓库名}`。请确认：
> 1. 当前仓库是否覆盖上述所有平台/模块？
> 2. 如果否，哪些部分可以在当前仓库完成？哪些需要其他团队/仓库处理？

根据用户回答，明确 Phase 1 文档的范围（通用的全局方案）和 Phase 2 的范围（当前仓库能做的部分）。

### 1.4 输出通用开发方案

输出一份结构化的 Markdown 文档，包含以下章节：

```
# 【开发方案】{需求名称}

## 1. 需求理解
- 功能目标
- 涉及平台/端
- 核心用户场景

## 2. 接口规格（如有 API 文档）
- 请求/响应结构
- 字段说明表
- 特殊约定

## 3. 业务规则
- 核心逻辑（伪代码或流程描述）
- 条件分支
- 格式化规则
- 异常处理

## 4. UI 交互规格（如有 UI 设计）
- 页面/组件清单
- 各组件的视觉规格摘要
- 交互行为描述
- 条件展示逻辑

## 5. 影响面总览
- 各端改动点概览（与项目无关的逻辑层面）
- 跨端统一的部分 vs 各端差异的部分

## 6. 多语言/国际化
- 哪些文案来自服务端（直接使用）
- 哪些文案需要客户端本地化

## 7. 验证清单
- 功能验证项
- 异常场景验证项

## 8. 决策点
> [DP-xxx] 标记需要人工确认的设计决策
>
> 每个决策点包含：现状描述、可选方案、建议、需确认的问题

## 9. 相关文档
- 需求文档链接
- UI 设计链接
- API 文档链接
```

**文档特点：**
- 与具体项目技术栈无关，任何端的开发者都能看懂
- 接口字段说明要详尽（这是各端共用的）
- 业务规则用伪代码表达，不绑定任何语言/框架
- 决策点（Decision Point）用 `[DP-xxx]` 标记，收集所有需要产品/设计/后端确认的问题
- 验证清单覆盖正常和异常场景

### 1.5 交付与确认

1. 将文档内容**在对话中以 Markdown 摘要/要点输出**（完整长文以文件为准亦可）。
2. **必须**按命名规范落盘：`{DOC_ROOT}/【开发方案】{需求短名}.md`
3. 如果用户主动要求上传为金山文档，再使用 `/wps-doc-cli` 的 `wps-doc import` 上传。不要默认上传。

等用户确认后，提示：

> Phase 1（通用开发方案）已完成。是否需要继续 Phase 2，输出落在当前项目的详细实施方案？

## Phase 2：项目实施方案

前提：Phase 1 已完成且用户确认要继续。

### 2.1 理解当前项目

需要深入了解当前仓库的技术细节，可并行探索以下方向：

**技术栈识别**
- 框架（Vue/React/Angular/iOS/Android…）及版本
- 状态管理方案（Vuex/Pinia/Redux…）
- 样式方案（Less/SCSS/Tailwind/StyleSheet…）
- 构建工具（Webpack/Vite/…）
- 包管理器（npm/yarn/pnpm/…）

**内部规范识别**
- 组件库（如 KDesign、Ant Design、Element UI…）及其设计变量
- 图标库
- 请求层封装（axios 实例、统一错误处理…）
- 路由方案
- i18n 方案
- 埋点/数据上报方案

**代码风格识别**
- 文件组织方式（按功能/按类型/按页面…）
- 命名约定（组件名、文件名、CSS 类名…）
- 现有相似功能的实现模式（找一个最接近的现有功能作为参照）

探索方法：
- 读 `package.json`（或 `Podfile` / `build.gradle` 等）了解依赖
- 读项目根目录的配置文件（`.eslintrc`、`tsconfig.json` 等）
- 浏览 `src/` 目录结构
- 找一个与当前需求最相似的已有功能，读其代码了解项目约定
- 检查是否有 `.cursor/rules/` 或项目级别的开发规范文档

### 2.2 输出项目实施方案

基于 Phase 1 的通用方案 + 当前项目的技术上下文，输出详细实施文档：

```
# 【实施方案】{需求名称} — {项目/端名称}

## 1. 概述
- Phase 1 方案引用
- 当前项目技术栈概要
- 本实施方案覆盖的范围（如果需求涉及多端，说明当前方案只覆盖哪个端）

## 2. 接口规格
（从 Phase 1 拷贝，保持一致性）

## 3. 业务规则
（从 Phase 1 拷贝，保持一致性）

## 4. 实施步骤（通用）
1. 查看当前项目技术栈和代码风格
2. 确认入口位置
3. 新增接口调用（调用时机、防抖/节流策略）
4. 新增数据管理层
5. 新增 UI 组件（明确使用项目已有的组件库）
6. UI 视觉规格分析（先分析再编码）
7. 实现业务规则
8. 添加本地化文案
9. 设计规范审查（编码后）
10. 测试验证

## 5. 各端/模块详细实施
（按当前项目实际需要改动的端/模块分节）

### 5.x {端/模块名}

#### 技术栈
#### UI 设计参考
> [AI 指令] 实施前读取哪些 UI 资源文件，输出视觉规格摘要

#### 入口位置
> [决策点 DP-xxx] 需要确认的布局/位置问题

#### 改动清单
| 文件 | 类型(新增/修改) | 说明 |

#### 交互与视觉规格
（落到项目组件库语言：具体用哪个组件、哪个 props、哪个 CSS 变量）

## 6. 验证清单
（从 Phase 1 拷贝 + 补充项目特有的验证项）

## 7. 注意事项
- 性能考虑
- 缓存策略
- 安全考虑
- 与现有功能的交互影响

## 8. 相关文档
```

### 2.3 关于 UI 视觉规格处理

如果项目使用了设计系统（如 KDesign），实施方案中必须包含：

1. **色值映射表**：设计稿中的固定色值 → 项目设计变量的映射
2. **可复用组件清单**：哪些 UI 元素可以用项目已有组件实现
3. **关键布局参数**：字号、间距、圆角等与项目设计变量的对应关系

这些映射应该写在文档中，作为后续编码的约束条件——而不是让编码者自己去猜。

如果有 UI 资源文件（设计图、CSS 规格导出），建议将它们存放到项目的文档目录中，并在实施方案里用 `[AI 指令]` 块告诉后续 AI 编码流程去读取哪些文件。

### 2.4 决策点模式

在方案中遇到需要人工确认的设计决策时，使用以下格式标记：

```markdown
> **[决策点 DP-{模块}-{序号}]** 简短描述
>
> 现状/背景：...
>
> 可选方案：
> 1. 方案 A：...
> 2. 方案 B：...
>
> 建议：...
>
> **请确认**：具体需要确认的问题
```

所有决策点在文档末尾汇总一份清单，方便逐项确认。

### 2.5 交付

1. 对话中输出实施方案要点（或全文）。
2. **必须**按命名规范落盘：`{DOC_ROOT}/【实施方案】{需求短名}[-{范围}].md`
3. 文内引用 Phase 1 时使用正式文件名（`【开发方案】…`），勿写临时路径或旧命名。
4. 如果用户主动要求上传为金山文档，再使用 `/wps-doc-cli` 上传。不要默认上传。

## 注意事项

1. **不要跳过 Phase 1 直接做 Phase 2**。即使用户说"帮我直接写实施方案"，也应先快速过一遍 Phase 1 的分析（可以精简），确保需求理解完整。

2. **决策点不能自己做决定**。遇到模糊或有多种方案的地方，标记为决策点交给用户确认，不要擅自选择。

3. **影响面评估必须和用户确认**。永远不要假设当前仓库能覆盖需求的所有部分。

4. **接口字段说明要详尽**。很多 bug 源于对接口字段含义的误解，宁可写多不要写少。
